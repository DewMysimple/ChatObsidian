# 启动骨架屏与配置检查解耦修复

## 目标

解释并修复仓库中心长时间停留在浅灰色骨架屏的问题，同时保持配置变化提示和首次扫描能力。

## 定位

- `get_dashboard` 原先在首次返回前同步执行 `obsidian::pending_change`。
- 该检查会扫描最近配置快照的 `.obsidian` 文件；本机针对多个仓库的只读测量显示单次快照约需 4.2–5.1 秒，慢磁盘时更长。
- 空目录首次启动还会在同一请求内执行完整仓库发现和 Markdown 标题索引，导致首屏等待整个文件树完成。
- React 的 `loading` 在 `get_dashboard` 返回前保持为 `true`，因此界面只能显示骨架屏；这不是仓库数量为零，也不是 WebView 崩溃。

## 修改

- `get_dashboard` 只读取现有 SQLite 目录、快速刷新注册表元数据和真实窗口状态，不再同步计算配置差异。
- 配置变化检查继续由 `App.tsx` 首屏后的单飞轮询执行，检查结果仍通过原有提示横幅展示。
- 空目录时先结束首屏加载，再由 Zustand `load` 自动触发后台扫描；扫描期间界面保持可操作。
- 版本同步升级至 `0.1.13`，发布脚本按既定规则覆盖 release exe 和 latest NSIS 包。

- `python -B wiki_memory/工具/memory_lint.py check`

## 结果与遗留

- 已有目录启动不再等待配置哈希检查后才绘制主界面。
- 首次启动不会因全量扫描阻塞界面，但仓库列表会在后台扫描完成后逐步可用。
- 配置差异检查仍受本地文件系统速度影响，只是不再阻塞首屏。

## 待确认长期记忆

- 候选：所有可能触碰大量本地文件的任务都不应位于首屏关键路径；暂作为当前架构事实记录，后续若用户确认可提升为独立决策。
